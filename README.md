# WebSockets



## Завдання 1: Чому HTTP недостатньо? Дослідження обмежень

### Відповіді на питання для роздумів:

* **Скільки HTTP-запитів робить WebSocket для встановлення з'єднання?**
  WebSocket робить **рівно 1 (один)** HTTP-запит, який називається (Handshake). Клієнт надсилає стандартний `GET`-запит із обов'язковими заголовками `Upgrade: websocket` та `Connection: Upgrade`. Якщо сервер підтримує цей протокол, він повертає відповідь із кодом `101 Switching Protocols`, після чого з'єднання трансформується у двосторонній WebSocket-канал, а HTTP-протокол більше не використовується.

* **Якщо в чаті 1000 користувачів і всі «поллять» кожну секунду — скільки запитів за хвилину отримує сервер? А при WebSocket?**
  * **При HTTP Polling:** Сервер отримуватиме 60000 HTTP-запитів за хвилину. Більшість із цих запитів будуть «пустими» (сервер повертатиме відповідь, що нових повідомлень немає), але сервер все одно витрачатиме колосальні ресурси процесора та мережі на обробку заголовків та перестворення TCP-сесій.
  * **При WebSocket:** Кількість HTTP-запитів після ініціалізації дорівнюватиме **0**. Сервер триматиме всього 1000 відкритих TCP-з'єднань. Трафік почне ходити лише тоді, коли реально з'явиться нове повідомлення. Це знижує навантаження на сервер у тисячі разів.

* **Назвіть 3 реальних застосування WebSocket:**
  1. **Месенджери та чати** (Telegram Web, Discord, чати підтримки) 
  2. **Багатокористувацькі онлайн-ігри (ММО)** (наприклад, Dota 2, CSGO,CSGO2,CSGO228 чи шутери)
  3. **Платформи для спільної роботи** (Google Docs, Figma, інтерактивні дошки завдань).



## Завдання 2: WebSocket Handshake — як HTTP перетворюється на WebSocket

### Ключові заголовки Handshake:

| Заголовок | Хто надсилає | Призначення |
| :--- | :--- | :--- |
| `Upgrade: websocket` | Клієнт | Прошу сервер перевести поточне з'єднання на протокол WebSocket. |
| `Connection: Upgrade` | Клієнт | Вказує, що це запит на обов'язкову зміну (модернізацію) протоколу. |
| `Sec-WebSocket-Key` | Клієнт | Випадковий base64-ключ (зазвичай 16 байт), який клієнт надсилає для верифікації сервера. |
| `Sec-WebSocket-Accept` | Сервер | Хеш-відповідь, згенерована на основі ключа клієнта. Підтверджує, що сервер зрозумів запит і підтримує WebSocket. |
| `Sec-WebSocket-Version` | Клієнт | Вказує версію протоколу WebSocket, яку використовує клієнт (сучасний стандарт — `13`). |
| `101 Switching Protocols`| Сервер | HTTP-статус відповіді, що означає: «Я приймаю твої умови і перемикаюся на новий протокол». |


### Відповіді на контрольні питання (Завдання 2):

* **Навіщо потрібен `Sec-WebSocket-Key`? Від чого він захищає?**
  Він потрібен не для шифрування даних, а для захисту від випадкових чи помилкових підключень застарілих HTTP-проксі або кешуючих серверів. Сервер бере цей ключ, додає до нього жорстко прописаний у стандарті рядок-константу (GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`), рахує від цієї суміші SHA-1 хеш і кодує його в Base64, відправляючи назад у `Sec-WebSocket-Accept`. Якщо хеші зійшлися, клієнт упевнений: сервер дійсно підтримує WebSocket, а не просто тупо повернув назад заголовки без реального перемикання протоколу.

* **Що означає код відповіді `101`? Чим він відрізняється від `200`?**
  * Код **`200 OK`** означає: «Запит успішно оброблено, тримай дані, з'єднання можна закривати або тримати для наступних звичайних HTTP-запитів».
  * Код **`101 Switching Protocols`** — це системна інформаційна відповідь. Вона означає: «Я повністю погоджуюся на твою пропозицію змінити правила гри. З цієї мілісекунди ми більше не спілкуємося мовою HTTP, а переходимо на протокол WebSocket».

* **Після успішного Handshake — HTTP протокол продовжує працювати чи «замінюється»?**
  HTTP протокол повністю **замінюється (модернізується)** і припиняє свою роботу для цього з'єднання. Повернення назад до HTTP всередині цієї TCP-сесії неможливе. З цього моменту в обидві сторони ходять виключно низькорівневі WebSocket-фрейми (frames) з мінімальним оверхедом (всього від 2 до 10 байт службових даних на кожне повідомлення замість важких кілобайтних HTTP-заголовків).

## Завдання 3: WebSocket фрейми — структура повідомлень

### 1. Доповнена таблиця Opcode:

| Opcode | Назва | Призначення |
| :--- | :--- | :--- |
| **0x1** | Text Frame | Текстові дані (кодуються суворо в UTF-8). |
| **0x2** | Binary Frame | Бінарні дані (масиви байтів, файли, аудіо, зображення тощо). |
| **0x8** | Close Frame | Запит на закриття з'єднання. Обидві сторони підтверджують вихід. |
| **0x9** | Ping Frame | Перевірка зв'язку (Heartbeat). Запит від однієї сторони, чи живий ще інший учасник. |
| **0xA** | Pong Frame | Відповідь на Ping. Підтвердження, що з'єднання працює і не зависло. |

### 2. Відповіді на контрольні питання:

* **Навіщо клієнт маскує (XOR) дані перед відправкою серверу?**
  Маскування потрібне для захисту проміжних мережевих пристроїв (застарілих проксі-серверів, роутерів, кеш-серверів), а не від хакерів. Якщо клієнт надішле чистий текстовий фрейм, якийсь старий проксі-сервер на шляху може помилково прийняти його за звичайний HTTP-запит і спробувати закешувати або розпарсити, що повністю зламає зв'язок (атака типу *Cache Poisoning*). Завдяки операції XOR дані перетворюються на «шум» для проміжних вузлів, а кінцевий WebSocket-сервер легко знімає маску за допомогою того самого ключа.

* **Чому сервер не маскує дані, що відправляє клієнту?**
  Згідно зі стандартом RFC 6455, маскування є обов'язковим **тільки** у напрямку *Клієнт → Сервер*. Відповідь від сервера йде назад клієнту по вже чітко встановленому, довіреному тунелю з'єднання, тому ризику помилкового кешування проміжними проксі-серверами немає. Якщо сервер надішле клієнту замаскований фрейм, браузер негайно розірве з'єднання з помилкою безпеки.

* **Що станеться, якщо сервер отримає Close Frame — він повинен закрити з'єднання одразу чи спочатку відправити у відповідь теж Close Frame?**
  Сервер зобов'язаний **спочатку відправити у відповідь свій Close Frame**, і лише після цього остаточно закрити поточне TCP-з'єднання. Це процедура «ввічливого закриття» (Closing Handshake). Якщо сервер просто розірве TCP-сокет без надсилання Close-фрейму у відповідь, клієнт розцінить це як раптовий збій мережі або аварійне вимкнення та викличе внутрішню помилку додатка (`onerror`).



### Відповіді на контрольні питання (Завдання 4):

* **Навіщо `CancellationToken.None`? Де він може знадобитися?**
  `CancellationToken.None` вказує системі, що ми виконуємо асинхронну операцію без можливості її примусового скасування ззовні, тобто готові чекати відповіді скільки завгодно. 
  У реальних проектах замість `None` передають токен життєвого циклу додатка. Якщо користувач закриє вкладку або сервер почне планово вимикатися, токен активується і всі завислі методи `ReceiveAsync`/`SendAsync` миттєво перервуться, не забиваючи пам'ять та потоки процесора.

* **Що означає `endOfMessage: true` у `SendAsync`?**
  Цей прапорець виставляє системний біт **`FIN`** (Final) у заголовку WebSocket-фрейму.
  * Якщо `true`: ми кажемо серверу, що це цілісне повідомлення (або його останній шматок). Сервер може відразу склеїти байти та віддати їх в обробку.
  * Якщо `false`: ми повідомляємо, що це лише частина (фрагмент) великого повідомлення. Сервер почне накопичувати байти у буфері й чекатиме наступних фреймів, поки не прилетить фрейм із `endOfMessage: true`.

* **Що станеться, якщо клієнт завершить програму без виклику `CloseAsync`?**
  Відбудеться аварійне розривання TCP-з'єднання на рівні сокетів (надсилання пакета `RST`). Оскільки сервер не отримає правильного `Close Frame`, його метод `ws.ReceiveAsync` раптово перерветься і викине виключення `WebSocketException` (з помилкою на кшталт "З'єднання було примусово розірвано віддаленим хостом"). Якщо на сервері цей момент не загорнутий у `try-catch`, програма сервера просто впаде.
